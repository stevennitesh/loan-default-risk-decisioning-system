## Design decisions for the corrected release

### 1. Historical comparison and development assessment

Define `historical_comparison` as the exact original seed-42 test IDs recovered from the saved historical model/split artifact. Define `development` as all remaining labeled applicants in the same source snapshot. `application_test` stays an unlabeled scoring-only population. If the original artifact is unavailable, reconstruct using the historical code/config and original ordered source snapshot and prove identity against surviving split evidence. A count or matching seed alone is insufficient. Stop manifest publication if exact identity cannot be established; do not substitute a newly generated population.

Persist exact IDs locally and publish only hashes/counts/metadata as curated evidence. The manifest records schema/protocol version, source snapshot fingerprint, ID/target population fingerprint, exact sorted membership hashes, generation code/config identity, creation time, and the historical-use limitation. Readers verify membership against the actual data. IDs must be non-null integral values; reject booleans, fractional values, duplicates, missing/extra members, wrong source population, and pairwise overlap rather than silently coercing them into valid IDs.

The recommended corrected protocol is nested assessment within `development`:

1. Freeze five stratified outer assessment folds, seed 42, before corrected candidate results are inspected. Each outer assessment applicant receives predictions from a complete workflow that did not use that applicant for any fitting or selection in that fold.
2. Within each outer-training population, make a deterministic stratified 70% base-fit / 15% calibration-fit / 15% method-and-policy-selection partition. Persist exact fold/role IDs. Use a seed derived deterministically from protocol seed and outer fold, and record it.
3. Tune preprocessing, base-model parameters, and any enabled feature selection by three-fold CV exclusively within base-fit. Fit transformations on the inner-training fold; early stopping may see only its inner-validation fold. Select hyperparameters on mean inner-validation average precision, then lower complexity and stable candidate ID for ties. Freeze the small candidate grid before the run. Refit the chosen base recipe on base-fit, then keep that fitted model fixed.
4. Fit each calibrator using only that fixed model's predictions on calibration-fit. Compare raw/sigmoid/isotonic on method-selection rows using the gain rule below. Model-family selection uses raw-score average precision on method-selection rows, with exact ties resolved by simpler family (constant, logistic, unweighted LightGBM, weighted LightGBM), then candidate ID. Calibration choice follows for the selected family. Record calibrated ranking metrics separately because isotonic ties can change them.
5. Derive configured scenario cutoffs only from method-and-policy-selection scores in the selected score space. `balanced` is the predeclared displayed default, not the largest utility found after assessment. The utility grid describes scenarios; it does not optimize a policy using outer outcomes.
6. Freeze the full fold workflow before scoring its outer assessment fold. No outer labels, feature ranking, score distribution, calibration diagnostics, or policy outcomes feed fitting or selection. Persist all fold predictions and selected identities. Aggregate only after all folds finish.
7. Build the final batch release by running the same internal base-fit/calibration-fit/method-selection recipe once on all `development`, with recorded seed 42. Keep the resulting base model and calibrator intact; do not refit the base on the union after calibration. Evaluate `historical_comparison` only through a separate explicit frozen-release evaluator.

The nested results estimate this specified selection procedure on the development population; they are not the performance of the single final fitted model, nor an untouched external validation. The historical comparison evaluates that final model but remains historically exposed. Present these evidence types separately. Historical adaptive exploration of the dataset remains a limitation even after nesting. The price of the transparent inner partitions is less data used to fit each final base model; a calibrated fold ensemble could use data more efficiently but is deferred to avoid introducing a different deployment/explanation contract.

Training and experiment entry points accept a validated role-bound population, not arbitrary labeled frames or an unrestricted DB load. Every fit/selection stage checks exact permitted membership and logs the input hash. Outer assessment and historical comparison IDs may enter only their named evaluators after workflow freezing. Development experiment outputs contain no historical-comparison metric columns. Shared SQL may compute deterministic per-applicant features for all populations, but learned imputation/encoding, global feature selection, population-derived cutoffs, and model fitting remain fold-local.

Stability defaults to the frozen nested protocol. Any extra seeds are declared before running, affect only development folds or fitting randomness, and never redefine historical comparison membership. Report procedure variability by fold/seed separately from bootstrap sampling uncertainty. Do not choose a new workflow using outer summaries and still call those same summaries an independent assessment of that choice; record a new exploratory protocol revision and the reuse limitation.

SHAP used for selection is a separate artifact with `purpose=development_selection`, raw feature identifiers, model digest, eligible-input hash, fold, sample seed, and feature schema. Ranking background/sample rows belong to the relevant base-fit/inner-training population. Display labels are presentation metadata, not reversible feature keys. Post-selection SHAP may explain either scoring population with explicit provenance, but such artifacts are rejected as selection inputs. The first corrected evidence run uses the full corrected feature surface; top-N selection remains disabled by default while its safe path is repaired and tested.

### 2. SQL obligation, time, and missingness meaning

Create SQL normalization layers reused by `05_feature_installments.sql`, `05b_feature_risk_pressure.sql`, `05c_feature_recency_deterioration.sql`, and `05d_feature_last_k_temporal.sql`. Keep Python orchestration and all applicant joins at one row per `(SK_ID_CURR, source_population)`.

Candidate obligation identity is `(SK_ID_CURR, SK_ID_PREV, NUM_INSTALMENT_VERSION, NUM_INSTALMENT_NUMBER)`. Profile missing keys and conflicting amounts/due dates within that identity. Before treating different versions of the same applicant/loan/installment number as independent obligations, inspect source column descriptions and measured examples. Default conservative rule: only unambiguous obligations with one known positive scheduled amount and one known due date enter payment-completion/coverage features. Conflicting or cross-version ambiguous obligations are excluded from those denominators and counted explicitly as ambiguous history. Do not select the maximum version or sum competing schedules without evidence of effective chronology. Document exclusion coverage; if it materially removes the intended feature family, stop that feature's promotion and record the unresolved source meaning rather than silently weakening the guarantee.

Payment rows represent observed cashflows, not repeated scheduled amounts. Sum observed valid cashflows for an unambiguous obligation once each; repeated identical rows cannot automatically be deduplicated because there is no proven unique payment-event ID. Profile and report their incidence and source interpretation. Unknown amount/date cashflows make completion status unknown unless the observed valid evidence already establishes the particular adverse event being measured. Never map unknown status to observed on-time or fully paid behavior.

Application-relative cutoff is day 0, using strictly pre-application history (`day < 0`; completed monthly histories require `MONTHS_BALANCE <= -1`). Due obligations and realized payments have separate inclusion predicates. Future payments cannot alter historical paid amount, completion date, late status, or remaining balance. Future scheduled obligations are excluded from repayment-history denominators; a future-burden feature is a separate explicit contract and is not needed for this correction. Source-relative day/month fields are availability proxies; they do not prove actual ingestion/knowledge timestamps. State that limitation instead of claiming fully point-in-time-correct lending data.

For a known obligation, scheduled amount enters the denominator once. Coverage is observed paid amount / positive scheduled amount; preserve ratios above 1 as overpayment rather than silently clipping. Known remaining amount is `max(scheduled - paid, 0)`. Underpaid means known total paid is below scheduled at cutoff, not one partial cashflow below the full schedule. Completion date is the first eligible date at which cumulative payment reaches scheduled amount, aggregating same-day cashflows first. Completed lateness and incomplete arrears age are distinct features. An unknown completion has no invented final delay. Counts/rates include known support and unknown/ambiguous support; absent history produces null rates and zero history counts.

Corrected installment last-three windows use three most recent unambiguous due obligations across the applicant, ordered by due day descending then complete obligation key. Latest-obligation metrics use that same contract; do not call them latest payment-event metrics.

Corrected POS/card windows mean the three most recent distinct observed applicant months, not necessarily three consecutive calendar months. Normalize account-month identity first; exact duplicate account-month records are a contract error unless explicitly resolved by source evidence. Aggregate all accounts within each selected month before forming the window. Applicant-month delinquency is any known account delinquent, false only when all relevant account statuses are known and non-delinquent, otherwise unknown. Average rates across known months, with known/unknown month support. For monetary ratios, sum numerator and denominator across eligible account-month observations with both operands known and positive required denominator; export support, then calculate ratio of sums. Credit-card utilization uses eligible balance/limit totals, not an unweighted mean of account ratios. Drawing-count summaries use monthly summed known counts and report completeness. Preserve nulls when no valid denominator exists.

The POS last-loan feature means most recently observed loan: order by latest eligible month, then `SK_ID_PREV` as deterministic tie break. Do not claim most recently originated loan. Existing recent-minus-lifetime deltas may remain with names explicitly saying that the reference overlaps recent history; compute on compatible normalized grains and disclose support. A change to disjoint older history is a separate prespecified feature experiment, not a silent relabeling.

### 3. Calibration, baselines, and exact ranking budgets

Use the same corrected features, population assignments, tuning budget, and preprocessing protocol for the primary controlled comparison: training-prevalence constant, unweighted logistic regression, unweighted LightGBM, and class-weighted LightGBM. The constant `q_train` is calculated only from the actual base-fit training labels. Both LightGBM controls use the same declared parameter grid; weighting is the controlled difference. No SMOTE or new model family is required. Preserve historical v1 numbers as history; if a corrected v1-feature-family ablation is useful, declare it before evidence generation and label it as a new corrected control, not a regeneration of frozen v1.

Fit sigmoid and isotonic separately on calibration-fit predictions for each nonconstant control and preserve its raw metrics. On method-selection rows, a candidate is eligible only if raw Brier minus its Brier is at least `0.0005`, with roundoff tolerance `1e-12`. Among eligible candidates, prefer sigmoid only if within `0.0005` of the best eligible Brier; otherwise choose the best. No eligible candidate means explicitly uncalibrated. Reject missing/duplicate/unknown methods and nonfinite or out-of-range Brier values. Do not retain the old `CALIBRATION_FIT_SPLIT` selector coupling in the corrected path. Fit requires both target classes; tiny fixtures use a documented smaller test protocol, never silent production fallback.

If uncalibrated is selected, call it raw ranking score, not calibrated probability, and omit the calibrated claim from presentation. Probability diagnostics are still permitted but do not transform that score into a validated financial PD. Record logit clipping and sigmoid input transform; isotonic clipping and the selected score space are release metadata.

Use one exact-budget contract for ranking and workload: for rate `r` in `[0,1]` and batch size `N`, `K=floor(r*N)`. Explicit integer `K` must be between 0 and N. Reject conflicting explicit K/r settings. Sort by score descending and applicant ID ascending for ties; labels never affect ranking. Ranking metrics always state score kind, N, requested rate, and actual K. Zero K produces zero selected outcomes but undefined precision/lift; no positives produces undefined capture. Empty or single-class slices expose counts and defined metrics, with undefined metrics null and a reason. Do not publish accidental NaN/Infinity or fabricated zero AUC. Decile boundaries use the same floor cumulative budgets so top-decile values reconcile; empty bins are allowed for tiny samples.

### 4. Simulated action policy and utility

Recommended policy for this release: `simulated_approve`, `manual_review`, `simulated_decline`, and `review_deferred`. These are scenario outputs, not actual underwriting actions. Highest-risk applicants are simulated declines and do not consume review capacity. This resolves the existing `high_priority_review` label without implying a second uncharged queue.

Keep the three named growth/balanced/risk-averse risk-preference scenarios and their current quantile pairs (0.85/0.95, 0.80/0.90, 0.70/0.80), derived only on method-selection scores in the policy's declared score space. Cutoffs are frozen before assessment/scoring; changing batch distribution never retunes them. Scores below low cutoff are simulated approvals; scores from low inclusive to high exclusive are eligible for review; scores at/above high cutoff are simulated declines. Equal learned cutoffs are permitted in the corrected schema and mean an empty middle band; do not invent adjacent-score fallbacks to force a queue. An all-tied batch still obeys this rule and reports degenerate bands.

Allocate at most `min(K, eligible_count)` reviews, sorted by policy score descending and applicant ID ascending. Eligible overflow becomes `review_deferred`, not automatic approval or decline. Bands remain distinct from actions: deferred rows retain medium risk. Capacity applies separately to each explicit `(batch_id, scoring_population, policy_id)` population; do not combine historical evaluation and Kaggle scoring into one budget. A user needing a shared operational batch must supply one explicit batch, not rely on hidden aggregation.

Export eligible, reviewed, deferred, unused-capacity, and violation counts; actual queue capture and precision; approval/outcome rates; simulated-decline capture; and action counts summing to N. Capture in the top K is a separate model-ranking metric. Binary confusion displays, if retained, explicitly use simulated decline as positive and all other actions as negative; they are not final lending-outcome confusion matrices. Also provide an action-by-target table.

The primary utility remains the existing partial-horizon simulation: `approved_good*M - approved_bad*L - actual_reviews*C`. Simulated declines and deferred applicants have zero booked utility at this horizon; reviewed loans have review cost only because no downstream approval/outcome is modeled. Say this adjacent to outputs. This is not a model of reviewer effectiveness, full lifecycle profit, or prevented losses. Do not optimize review allocation by this incomplete utility or call the selected queue economically optimal.

Keep illustrative defaults M=1000, L=5000, C=50, r=0.10 in scenario utility units. Report a named no-review baseline with identical cutoffs and all would-be review cases deferred, and an approve-all baseline under the same M/L accounting. The former makes the cost-only nature of review explicit; do not hide its advantage under this partial horizon. On labeled populations, utility uses observed targets; on unlabeled scoring, observed-label utility and outcome capture are unavailable, never borrowed from another population. If expected utility using calibrated p is additionally shown, use a separate field/label and record the assumptions; it is not the realized-label metric.

Sensitivity minimum: M fixed at 1000, L/M in {2,5,10}, C in {0,50,100}, r in {0,0.05,0.10,0.20}, across the three frozen-cutoff scenarios. Show changes without selecting a headline winner after viewing comparison labels. Reviewer `g/b` assumptions and positive-review-gain allocation are deferred: they require an explicitly chosen simulation extension and new acceptance, not invented estimates from Home Credit.
